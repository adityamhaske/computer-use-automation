DOCS / GETTING STARTED

Quick Start

Get the system running in under a minute.

Prerequisites

  • Python 3.11+
  • uv (optional, used if present; otherwise venv + pip)

Setup

# Clone and enter the project
git clone https://github.com/adityamhaske/interface.ai.git
cd interface.ai

# Install everything: venv, dependencies, Chromium
make setup

Configuration

cp .env.example .env

The only thing that needs an API key is the live discovery run. Replay, escalation, the full test suite, and the demo all work without one.

VariablePurpose
OPENROUTER_API_KEYDiscovery only. Any OpenAI-compatible gateway works.
CUA_LLM_BASE_URLDefaults to OpenRouter
CUA_LLM_MODELModel ID for discovery
CUA_POLICY_FILEAllowlist and risk policy — defaults to config/policy.yaml

Run the demo

# The whole story, one command — twelve stages end to end
make demo

Takes about a minute. Works without an API key — discovery falls back to a recorded transcript and says so explicitly.

Unified Orchestrator (./start.sh)

./start.sh                 # Default: setup venv + run the full 12-stage demo
./start.sh ui              # Launch Human-in-the-Loop Web Console + Mock Bank
./start.sh ui --headed     # Run the console with visible (headed) Chromium
./start.sh app             # Run hostile mock back-office app (port 8811)
./start.sh app-b           # Run rebranded second-tenant variant (port 8811)
./start.sh check           # Run CI checks: lint + typecheck + invariants + tests
./start.sh test            # Run offline test suite (no API keys, no network)
./start.sh eval            # Run stability and cross-tenant drift evaluations

Development commands (Makefile)

make check          # lint + typecheck + invariants + tests (CI)
make test           # offline suite; no API key, no network
make invariants     # just the architectural contracts
make eval           # stability + cross-tenant measurement

244 tests, mypy --strict clean, five enforced import contracts. The whole suite runs offline with no API key.

Fault injection

Faults are injected into the mock app, not the replay engine — the executor must not know a fault is coming:

# Arm a fault

  -d '{"fault":"transient_load","count":1}' \
  -H 'content-type: application/json'

# Reset
curl -X POST localhost:8811/_control/reset

Available faults: transient_load, session_timeout, undeclared_dialog, validation_error.

DOCS / ARCHITECTURE

Execution Pipeline

One path to a surface, for every actor. Discovery, replay, and human intervention all take the same path.

Action ──► TargetResolver ──► PolicyEngine ──► SurfaceDriver
       (resolve or refuse)    (authorize)      (dispatch)

Enforced three independent ways:

  1. Import rule. cua.runtime.dispatcher is the only module allowed to import cua.surfaces (.importlinter contract policy-chokepoint).
  2. Type rule. SurfaceDriver.dispatch() accepts only an AuthorizedAction, which carries a token instance held exclusively by PolicyEngine.
  3. Reconciliation test. Every dispatch event in a run record must have a matching authorize event with the same action ID.

Human input is policed, not injected

The console submits raw_input actions which traverse the same path under a distinct HUMAN policy profile:

AUTOMATIONHUMAN (during intervention)
Domain allowlistenforcedenforced
safe actionsallowallow
elevated actionsallow if declaredallow, recorded
irreversible actionsblock → escalateallow with confirmation, recorded
Off-artifact navigationNAVIGATION_BLOCKEDallowed within allowlist, recorded
Evidence redactionappliedapplied

The Ten Invariants

The value of this system is almost entirely in a handful of properties. Each is mechanically enforced — the test is named so you can see it fail on purpose.

1. Replay never calls or imports the LLM

cua.replay may not import cua.agent, httpx, or any model client — directly or transitively. A replay that can quietly ask a model for help is not deterministic, not cheap, and not auditable.

2. No action reaches a driver without policy authorization

cua.runtime.dispatcher is the only module permitted to call dispatch(). SurfaceDriver.dispatch() accepts only an AuthorizedAction, which carries a token that only PolicyEngine can mint.

3. Target identity is a semantic TargetDescriptor, never a raw CSS selector

Artifacts describe controls by role, accessible name, scope, structural anchor, and ordinal. Surface-specific data may appear only inside TargetDescriptor.hints, and a hint is an unverified cache.

4. Human input cannot bypass policy or evidence

The operator console never injects into the page. It submits raw_input actions to the SessionBroker, which runs them through the same chokepoint under the HUMAN policy profile.

5. Unknown states fail closed

If the observed UI matches no declared precondition, checkpoint, outcome, or recovery rule, it is UNEXPECTED_STATE and the run stops. If a target resolves ambiguously, the resolver refuses with TARGET_AMBIGUOUS.

6. Every sink is redacted

Logs, artifacts, evidence files, screenshots, and outbound LLM prompts. Secrets are {$secret: ref} references resolved at dispatch time and never written anywhere.

7. Business outcomes are not failures

"No such member" is a legitimate answer the caller needs, not a crash. BUSINESS_OUTCOME exits 0.

8. Automation may only act while it holds the session

Every dispatch asks the lease: who holds this session, and has it changed hands since this run was authorized. Either answer can refuse the dispatch with LEASE_LOST.

9. Capabilities are immutable

A Capability at id@version is frozen and content-hashed. Anything that changes because you ran it lives in a separate document: RunRecord, CapabilityEvaluation, CapabilityApproval.

10. domain/ is pure

No I/O, no network, no browser, no clock. cua.domain imports nothing else from cua.

DOCS / DESIGN

The Capability Artifact

The unit of reuse in this system. What the LLM's discovery run compiles down to, what a human reviews, and what an AI agent invokes in production.

Decision rationale lives in ADR 0002. This document is the reference for what the schema is.

Three readers, one artifact

ReaderNeeds
Replay engineUnambiguous, executable steps with explicit success and failure conditions
Human reviewerTo understand what it does, what it touches, and what could go wrong — without running it
Calling AI agentA typed contract: what to pass, what comes back, what can happen

Document family

Only the first is the capability. The rest exist so the capability can stay immutable.

cua.capability/v1             frozen, content-hashed — the contract
cua.tenant_binding/v1         per-tenant vars + step overrides (base ⊕ overlay)
cua.run_record/v1             one execution: trace, resolutions, drift, evidence refs
cua.capability_evaluation/v1  aggregate over runs: stability, strategy mix, drift trend
cua.capability_approval/v1    draft → approved, approver, scope

Identity

capability:
  id: "corebank.member.savings_balance"   # <vendor-product>.<domain>.<operation>
  version: "1.2.0"
  content_hash: "sha256:…"

id is namespaced by vendor product, never tenant — the precondition for cross-tenant reuse.

Typed contract

inputs:
  - { name: member_id, type: string, required: true, pattern: "^[0-9]{4,10}$",
      sensitive: false, example: "12345" }
outputs:
  - { name: savings_balance, type: money, source: { step: read_balance } }

These emit JSON Schema directly, so the artifact is the agent tool contract — there is no second source of truth to drift. sensitive: true propagates everywhere.

Steps

steps:
  - id: enter_member_id
    action: { type: type, value: { $input: member_id } }
    target:
      role: textbox
      name: { match: exact, value: "Member Number" }
      scope: { frame: content, region: search_form }
      anchor: { relation: row_of, cell_text: "Member Number" }
      hints: { css: "...", node_path: "..." }   # unverified cache
      fingerprint: "sha256:…"
      recorded_strategy: semantic_exact
    precondition:  { assert: node_exists, role: textbox, name: "Member Number" }
    wait:          { for: snapshot_stable, timeout_ms: 5000 }
    postcondition: { assert: node_has_value, value: { $input: member_id } }
    risk: safe

Every step asserts both before and after. A step that only acts is a step that assumes the click worked.

Success, outcomes, recovery

# Did we actually reach the state we wanted?
checkpoint:
  all_of:
    - { assert: node_exists, role: heading, name_contains: "Member Detail" }
    - { assert: node_matches, role: cell, name_matches: '^\\$[0-9,]+\\.[0-9]{2}$' }

# Legitimate answers — NOT failures
outcomes:
  - { code: member_not_found, detect: { text_present: "No records found" },
      terminal: true, returns: { member_id: { $input: member_id } } }

# Bounded, declared remediation — never open-ended
recovery:
  - { id: transient_load, detect: { http_status_in: [502,503,504] },
      remedy: [ { reload: {} } ], max_attempts: 3, backoff: exponential }
DOCS / DESIGN

Target Resolution

Resolution is where determinism is won or lost. Turning a semantic TargetDescriptor into a concrete UiNode in the current snapshot.

The resolution ladder

Strategies are tried in fixed order. The first that yields exactly one candidate wins.

#StrategyMatches onSurvives
1semantic_exactrole + accessible name, exact, unique in scopemost things
2semantic_normalizedsame, case/whitespace/punctuation foldedcosmetic label edits
3structural_anchorposition relative to nearby textcontrols with no usable name at all
4hint_cachedstored CSS/node-path hintnothing structural; speed optimization
5ordinal_in_regionNth control of a role within a scoperebranding; last resort before refusal
6visionOCR / bounding boxdiscovery only — hard-disabled in replay

Rung 3 is what makes legacy enterprise apps tractable. Those apps are full of controls with no name, no label, and no test ID, sitting in a table cell next to the text that identifies them.

Rung 4 is a cache, not an identity. A hint is accepted only if the node it resolves to also satisfies the semantic assertion.

Ambiguity is refusal

If two or more candidates survive above the ambiguity threshold, the resolver raises TARGET_AMBIGUOUS and the run stops. It does not pick the first, the topmost, or the highest-scoring.

Two plausible "Submit" buttons mean the screen is not what we think it is, and acting on either is how an automation posts a transaction to the wrong account. A refusal is recoverable — a wrong click may not be.

Drift

Resolving via a lower-priority strategy than the one recorded at discovery is drift — a signal, not a silent success. Per-step drift aggregates into a run-level drift_score.

This is the mechanism behind the multi-tenant story: a tenant whose UI has diverged shows rising drift before replays begin to fail.

Variant B: two kinds of divergence

Case A — markup churn, same vocabulary (the ladder handles this)

BaseVariant B
accessible nameMember NumberMember Number — same
form field namememnomember_num — changed
CSS classfrmfldng-inp — changed

semantic_exact resolves it on both. This is the falsifiable form of "this system does not depend on CSS selectors."

Case B — rebranding, different vocabulary (this needs an overlay)

BaseVariant B
balance labelSavings BalanceSavings Bal.
account typeAccount TypeType of Account

No automatic recovery here — and that is correct. Inferring that "Savings Bal." means "Savings Balance" is a fuzzy guess, and a system that guesses which row holds a balance will eventually read the wrong one.

Error Taxonomy

Two distinct type families — what we observed, and how the run ended — because they are not the same axis.

What we observed (a classification of a moment)

ObservationClass = EXPECTED | BUSINESS_OUTCOME | RECOVERABLE | HARD_FAILURE | UNEXPECTED_STATE

How the run ended (a terminal status)

RunStatus = SUCCESS | BUSINESS_OUTCOME | NEEDS_HUMAN | FAILED

The decision procedure

At every observation point the executor asks, in this order:

1. Does the state satisfy the step precondition / checkpoint?   → EXPECTED, proceed
2. Does it match a declared `outcomes` detector?                → BUSINESS_OUTCOME, return
3. Does it match a declared `recovery` detector?                → RECOVERABLE, remediate
4. Is it a known hard-failure condition?                        → HARD_FAILURE, stop
5. Otherwise                                                    → UNEXPECTED_STATE, FAIL CLOSED

PRECONDITION_FAILEDStep entry condition unmetPrior step didn't land
CHECKPOINT_FAILEDFlow complete, success falseHappy path not reached
ACTION_FAILEDDriver couldn't perform actionControl disabled, obscured

NAVIGATION_BLOCKEDAllowlist violationOff-domain redirect
POLICY_DENIEDPolicy refused the actionIrreversible without approval
RECOVERY_EXHAUSTEDOutlived max_attemptsPersistent, not transient

DOCS / DESIGN

Control Transfer (Human-in-the-Loop)

A human takes control of the same live session the automation was using — not a fresh one — does the manual work, and hands it back so the run can finish.

State machine

RUNNING ──escalate──► PAUSED ──human_claim──► HUMAN_CONTROL
   ▲                  (epoch++)               (epoch++)
   │                                                │
   └── RESUMING ◄── re-anchor + reconcile ◄── human_release (epoch++)

The lease

Lease(holder: Actor, epoch: int, expires_at: datetime)

holder ∈ {AUTOMATION, HUMAN, NONE}. Every transition increments epoch monotonically. Every dispatch() asserts lease.held_by(actor, epoch).

Escalation triggers

TriggerMeaning
TARGET_AMBIGUOUSResolver refused to guess
TARGET_NOT_FOUNDLadder exhausted
CHECKPOINT_FAILEDReached the end, didn't reach the state
RECOVERY_EXHAUSTEDA transient condition wasn't transient
UNEXPECTED_STATEFail-closed default
risky_action_unapprovedIrreversible action needs human approval

Re-anchoring after handoff

On human_release the executor:

  1. Snapshot-diffs pre-handoff against post-handoff → records human_delta
  2. Re-evaluates preconditions from the current step forward
  3. Skips forward to the first step whose precondition isn't satisfied — doesn't redo human work
  4. If the state matches no step's precondition → UNEXPECTED_STATE, fails closed

Step 4 is the fail-closed rule applied to the handoff seam. "The human left the session somewhere I don't recognize" is exactly the moment not to improvise.

DOCS / DECISIONS

ADR 0001 — UiSnapshot as the cross-surface abstraction

Status: Accepted · 2026-09-11

Context

We must perceive and act on three very different kinds of surface: modern web apps, legacy server-rendered web apps (framesets, nested tables, non-semantic markup, no test IDs), and native desktop applications.

Three candidates: DOM/CSS first (breaks on desktop), pure vision (pixel coordinates are the least stable thing you can persist), and semantic/accessibility tree.

Decision

Perception normalizes every surface into a UiSnapshot: a tree of UiNode {node_id, role, name, value, states, bounds, scope, parent, hints}.

The artifact schema and targeting system depend only on UiSnapshot and TargetDescriptor. Neither knows what an accessibility tree, a CDP session, or a DOM is.

DriverPopulates UiSnapshot from
PlaywrightCdpDriver (built)CDP Accessibility.getFullAXTree + box model, enriched with DOM-derived hints
DesktopUiaDriver (stubbed)Windows UI Automation element tree
Future OCR driverVision model + OCR over a screenshot

Consequences

Good. The same artifact can replay on a desktop driver, because role: button, name: "Search" means the same thing in UIA as in ARIA.

Bad. Accessibility trees on genuinely hostile legacy apps can be thin. Mitigated by driver-level enrichment and the structural_anchor resolution strategy.

DOCS / DECISIONS

ADR 0002 — Immutable content-addressed capability

Status: Accepted · 2026-09-11

Context

A capability artifact accumulates pressure to hold more: run counts, stability scores, approval state, last-run timestamps. An earlier draft put telemetry inside the capability. Two problems surfaced:

  1. The definition mutates every time you run it — git diffs become noise
  2. "Which version produced that run?" becomes unanswerable

Decision

A Capability at id@version is frozen and content-hashed. Nothing that changes as a result of executing it may live inside it. Runtime state moves into separate documents.

Consequences

Good. Reviewing a capability is reviewing a contract. A RunRecord can name exactly what it executed.

Also good. Immutability makes the multi-tenant story cleaner: a tenant cannot "drift" a shared capability by using it.

ADR 0003 — Four-class observation taxonomy

Status: Accepted · 2026-09-11

Context

A replay observes a screen and must decide what it means. The brief asks us to distinguish business outcomes, recoverable conditions, and hard failures. Working through the mock app exposed a fourth case: a state this capability does not understand.

A system without this category has to force it into one of the other three. The tempting choice is "keep going and see." That is precisely the behaviour that causes incidents.

Decision

Two distinct type families:

ObservationClass = EXPECTED | BUSINESS_OUTCOME | RECOVERABLE | HARD_FAILURE | UNEXPECTED_STATE
RunStatus = SUCCESS | BUSINESS_OUTCOME | NEEDS_HUMAN | FAILED

Consequences

Good. The caller's contract is honest: BUSINESS_OUTCOME(member_not_found) exits 0 and returns data. A FAILED carries enough detail to fix without reproducing.

Bad. Authoring a capability requires declaring outcomes and recovery rules explicitly — more work than letting the executor improvise. That is the point.

DOCS / DECISIONS

ADR 0004 — A single, type-enforced policy chokepoint

Status: Accepted · 2026-09-11

Context

Three different actors want to act on the live session. An earlier draft forwarded human clicks directly via CDP — which meant the moment a human took over, the allowlist, risk classification, and evidence trail all stopped applying.

Decision

One path to a surface, for every actor: Action → TargetResolver → PolicyEngine → SurfaceDriver.

Enforced three independent ways (import rule, type rule, reconciliation test), because an invariant everyone agrees with is weaker than one nobody can violate.

Consequences

Good. Discovery, replay, and human intervention are the same code path, differing only in who originates the action — so the guardrails we test are the guardrails that run.

Bad. raw_input is awkward to police semantically. We evaluate on coarse attributes and say so as a stated limit.

DOCS / DECISIONS

ADR 0005 — Tenants overlay a capability; they never fork it

Status: Accepted · 2026-09-11

Context

The economics of this system: if automating a flow for one credit union means re-recording it for the next 200, the product does not work.

Decision

Capabilities are namespaced by vendor product, not by tenant. Per-tenant differences are expressed as overlay documents.

# cua.tenant_binding/v1
capability_ref: "corebank.member.savings_balance@1.2.0"
tenant: first-valley-cu
vars: { base_url: "https://fvcu.internal" }
overrides:
  steps:
    enter_member_id:
      target: { name: { match: exact, value: "Member #" } }

Drift is measured, not assumed. Descending the resolution ladder at replay is a drift signal, not a silent success.

Consequences

Good. A rebranded label costs a four-line overlay, not a re-record. The drift score tells us which tenants are diverging before replays start failing.

DOCS / PRODUCT

Product Requirements

Problem, users, requirements, success criteria, and scope.

Thesis: discovery is probabilistic; execution is deterministic.

Problem

Banks and credit unions run a long tail of back-office applications with no API: core banking screens, servicing tools, admin consoles. When an AI agent needs to get real work done, the only way in is to drive the UI the way a human operator would.

Doing that with an LLM on every invocation is slow, expensive, non-deterministic, and unauditable — three of which are disqualifying in a regulated environment.

Users

UserNeeds
A calling AI agentInvoke a capability by name with typed arguments and get a typed result back
A human reviewerRead a capability and understand what it does, without running it
A human operatorTake a stuck session, control it, and hand it back
An engineer on callRead a failure and know: what step, what was expected, what was observed

Requirements

#Requirement
R1Accept a natural-language goal + target; run an LLM observe→decide→act loop against a live UI
R2Emit a typed, versioned, serializable artifact: ordered steps, typed I/O, success checkpoint
R3Replay that artifact deterministically with no LLM in the decision loop
R4Distinguish business outcomes from recoverable conditions from hard failures
R5Enforce a configurable allowlist; classify risky actions; never persist secrets or raw PII
R6Produce evidence: a structured log of what happened and why
R7Detect "stuck", route an intervention, let a human take the live session and hand it back
R8Design a credible answer for heterogeneous surfaces and multi-tenant reuse

Success criteria

  1. A real LLM discovery run exists in /evidence/
  2. The artifact schema is genuinely good — typed I/O, semantic targeting, asserted checkpoint
  3. Replay demonstrably never touches the LLM, and a fault matrix shows the taxonomy working
  4. A human really takes over the live session and the run resumes
  5. REPORT.md defends the trade-offs under the seven mandated headings

Run a Discovery

Discovery is the probabilistic half: an LLM drives a live UI to a goal and we record what it did. It is the expensive path, run once per capability.

Prerequisites

cp .env.example .env     # set OPENROUTER_API_KEY
make app                 # the mock back-office on :8811

Run

cua discover \
  --goal "Look up member 12345 and read their current savings balance" \
  --target http://localhost:8811 \
  --out evidence/capabilities/

What happens

  1. The driver observes the surface and normalizes it into a UiSnapshot
  2. The snapshot is rendered for the model — not raw HTML, and redacted on the way out
  3. The model emits a tool call from the closed action space. It cannot invent an action
  4. PolicyEngine authorizes it. Off-allowlist or irreversible actions are blocked
  5. The resolver resolves the target; the dispatcher dispatches; the bus records everything
  6. Loop until the goal is met or a stop condition fires
  7. On success, the compiler emits a draft Capability

Output

evidence/discovery/<run_id>/
  trace.jsonl        authorize / resolve / dispatch / observe, actor-tagged
  snapshots/         UiSnapshot per step
  screenshots/       redacted
  run_record.json    status, timings, budget
evidence/capabilities/<id>@<version>.yaml

If it fails

SymptomLook at
Stops at max_stepsthe llm_call events in trace.jsonl — is it looping on one screen?
POLICY_DENIEDExpected if the goal needs an irreversible action
TARGET_AMBIGUOUSThe screen genuinely has two matching controls. Good — it refused.
Model can't find a controlCheck the UiSnapshot in snapshots/

Run a Replay

Replay is the deterministic half: the production execution path. No model, no decisions, no surprises.

make app
cua replay evidence/capabilities/corebank.member.savings_balance@1.0.0.yaml \
  --input member_id=67890

Exercising error paths

cua replay <artifact> --input member_id=99999           # BUSINESS_OUTCOME(member_not_found)
cua replay <artifact> --fault transient_load            # RECOVERABLE → SUCCESS
cua replay <artifact> --fault transient_load --always   # RECOVERY_EXHAUSTED
cua replay <artifact> --fault undeclared_dialog         # UNEXPECTED_STATE → fails closed
cua replay <artifact> --fault session_timeout           # re-auth or escalate

Debugging a failure

FailureUsual cause
TARGET_NOT_FOUNDThe screen isn't what the artifact expects
TARGET_AMBIGUOUSDescriptor too loose, or genuinely two matches
CHECKPOINT_FAILEDSteps ran but goal state wasn't reached
UNEXPECTED_STATECapability doesn't declare this screen
RECOVERY_EXHAUSTEDThe "transient" condition wasn't transient

Determinism

Same artifact + same inputs + same app state ⇒ identical decision trace. If two replays diverge, that is a bug in this system, not flakiness.

Handle an Escalation

A run stopped because it could not safely proceed. This is a designed outcome, not a crash.

Taking control

cua console          # http://localhost:8812

Claim takes the lease. The lease epoch increments, and any in-flight automation dispatch is refused with LEASE_LOST.

You are driving the same live session, not a copy.

What you can and cannot do

You, during an intervention
Domain allowlistStill enforced
Ordinary actionsAllowed, recorded
Irreversible actionsAllowed with explicit confirmation, recorded
EvidenceEverything captured, tagged actor=HUMAN

Handing back

Release returns the lease. The executor then:

  1. Diffs session state → records human_delta
  2. Re-evaluates preconditions from the current step forward
  3. Skips forward to the first step whose precondition isn't satisfied
  4. If the state matches no step's precondition → stops with UNEXPECTED_STATE

Afterwards

A recurring escalation is a capability defect, not an operations problem. Usual fixes:

  • Screen seen repeatedly but undeclared → add an outcomes or recovery entry
  • TARGET_AMBIGUOUS on the same step → tighten the descriptor
  • Rising drift_score for one tenant → add a TenantBinding overlay, or re-record
